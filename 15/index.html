    第 15 天 - 深入软件仓库

    • 教学视频：Lesson video（英文）
    • 补充视频：Application repositories（英文）

    引言

    课程早期，你已经用 apt install 在服务器上装过一些软件包了。那过程相当轻松，我们也解释过：Linux 的软件安装模式和 Android、iPhone 上的“应用商店”非常相似——macOS 和 Windows 也越来越走这条路。

    不过今天，你要掀开“盖子”看看这套机制究竟是怎么工作的；更好地理解它的优点（以及缺点！）；还要看看如何在主要官方源之外安全地扩展系统。

    今日任务

    • 添加一个新仓库
    • 移除一个仓库
    • 弄清楚到哪里去找某个程序（apt search）
    • 不用 apt 安装程序

    软件仓库与版本

    任何一个具体的 Linux 安装都有几个重要特征：

    • 版本——例如 Ubuntu 20.04、CentOS 5、RHEL 6
    • “位数”——32 位还是 64 位
    • 芯片——Intel、AMD、PowerPC、ARM

    版本号尤其重要，因为它决定了你能安装的应用程序版本。Ubuntu 18.04 发布时（2018 年 4 月——版本号正是这么来的！），自带的是 Apache 2.4.29。所以，如果你的服务器跑的是 18.04，那怕五年之后才用 apt 安装 Apache，拿到的也依然是这个版本。这带来了稳定性，但对那些渴望新版本才有的特性的 Web 开发者来说，代价也是明摆着的。仓库*确实*会打安全补丁，不过方式是把新版本里的安全修复“向后移植”（backport）到最初发布的老稳定版本中。

    这些配置都在哪里？

    我们下面讨论的是 Debian、Ubuntu 发行版以及数十个衍生版所用的“包管理器”。它使用 apt 命令；不过在大多数场景下，Red Hat 家族（RHEL、Fedora、RockyLinux、CentOS 等）使用的 yum 和 dnf 命令工作方式也非常相似——其他发行版里的同类工具也是如此。

    配置由 /etc/apt 目录下的文件完成。想看你安装的软件包来自哪里，用 less 查看 /etc/apt/sources.list.d/ubuntu.sources，你会看到为你的具体版本指定仓库 URI、套件（suite）和组件（component）的条目：

         Types: deb
     URIs: http://archive.ubuntu.com/ubuntu/
     Suites: noble noble-updates noble-backports
     Components: main restricted universe multiverse

    Debian 及其他基于 Debian 的发行版仍然直接在 /etc/apt/sources.list 里用单行配置，但参数是一样的：

    • 软件包类型：deb
    • URI（源）：最常见就是一个用来拉取软件包的网址
    • 套件（Suite）：发行版版本的代号，比如 Ubuntu 24.04 叫 Noble，22.04 叫 Jammy，等等
    • 组件（即实际的仓库）：你从这个仓库里拉取的是哪一套软件包，“main”或者另外某些

    译注：原文此处笔误写作 26.04，已更正——Jammy Jellyfish 是 Ubuntu 22.04 的代号。

    一个 sources.list 行的例子——为 Debian 13（trixie）从 main 和 non-free-firmware 仓库拉取 deb 包：

    deb http://deb.debian.org/debian trixie main non-free-firmware

    眼下不必纠结这些语法的细节，不过相当常见的诉求是想添加额外的软件仓库——这正是我们接下来要处理的。

    额外软件仓库

    主仓库包含操作系统运转所必需的核心软件包，包括内核、基础工具和关键库。虽然这些仓库里可用的软件数量已经惊人，但仍常有软件包不在其中，因为它们被认为*非必需*。这些包通常会按以下标准被分进不同的仓库：

    • 稳定性：新软件包最初进入的 unstable 仓库可以充当滚动发布流，而官方支持的重心更多放在 main 这类 stable 仓库上——里面的包经过了充分的 bug 与冲突测试。
    • 理念：软件能否以自由许可证提供（这里的 free 指自由，而非免费）；专有应用和非自由固件通常会被推向单独的仓库。

    接下来，你就往系统里添加一个额外的仓库，并从它安装软件。

    启用额外的软件仓库

    先快速检查一下你*现在*就能安装多少软件包。运行下面的命令可以拿到完整列表和细节：

    apt-cache dump

    ……不过你会想多按几次 Ctrl-c 把它停下来，因为输出实在过于冗长。

    更省事的做法是用 grep 只把包名过滤出来，再用 wc -l 计数（wc 是“word count”，-l 让它数行而不是数词）——像这样：

    apt-cache dump | grep "Package:" | wc -l

    这些就是你现在能安装的全部软件包。有时，启用额外的仓库后还会有更多软件包可用。大多数 Linux 发行版都有类似的概念；在 Ubuntu 里，“Universe” 和 “Multiverse” 仓库默认常常是关闭的。它们同样由 Ubuntu 托管，但支持较少；而 Multiverse：“包含被归类为非自由（non-free）的软件……可能不包含安全更新”。Multiverse 里的实用工具，比如有压缩工具 rar 和 lha，还有网络性能测试工具 netperf。

    要启用 “Multiverse” 仓库，你可以参考 Ubuntu 社区指南，但基本上你只是在 apt 源文件里*为该仓库添加一条登记*。

    添加之后，更新本地可用软件的缓存：

    sudo apt update

    完成后，用例如 apt-cache search netperf 这样的命令搜索你要找的应用，而不必手动翻那份 dump 列表。你会看到一个更短的列表，给出相关软件包的名字和一行简短描述。

    然后这样检查 netperf：

    apt-cache policy netperf

    ……输出会显示它来自 Multiverse。

    netperf:
  Installed: (none)
  Candidate: 2.7.0-0.1
  Version table:
     2.7.0-0.1 500
        500 http://mirrors.digitalocean.com/ubuntu noble/multiverse amd64 Packages

    添加其他仓库

    有些软件仍以 deb 包格式提供，却不在任何官方源里——也就是说，它并非来自 Debian 或 Ubuntu 的服务器。这种情况下有两种可能：

    • 只提供了 deb 包，你得用 dpkg 手动安装（见下文）
    • 开发者公司提供了仓库源及其 GPG 签名密钥，这样你就可以添加这样一条登记：
    Types: deb
URIs: https://brave-browser-apt-release.s3.brave.com
Suites: stable
Components: main
Architectures: amd64 arm64
Signed-By: /usr/share/keyrings/brave-browser-archive-keyring.gpg

    通常会有说明告诉你如何下载并验证 GPG 签名（或者干脆给你一个代劳的脚本）。再强调一次：凭常识行事，只从可靠的来源下载。

    另外提一句，PPA（Personal Package Archives，个人软件包归档）曾是一种获取未能进入官方仓库的额外软件包的途径，但在 Snap 和 Flatpak 这类现代应用商店普及之后，它已经过时了。

    apt 与 dpkg

    你下载了一个 .deb 文件，想安装它。能用 apt 来处理吗？

    嗯，能。

    apt（Advanced Package Tool）是高级包管理器，负责解决依赖关系；而 dpkg（Debian Package）是直接处理 .deb 文件的低级工具。

    所以，下面两种方式任选其一，都可以手动安装 deb 包：

    dpkg -i /path/to/package/name.deb
apt install /path/to/package/name.deb

    Debian/Ubuntu 生态之外的软件包

    可如果我想用的应用没有 Debian/Ubuntu 版本怎么办？

    你还有机会！看看这个应用在 Snap 或 Flatpak 里有没有。这两种格式通用且跨发行版，每个软件包都自带全部依赖。你需要安装 Snap 才能从 Snap Store（集中式，由 Canonical 开发）下载，或者安装 Flatpak 从 FlatHub（去中心化、社区维护的生态）之类的地方拉取软件包。

    无论如何，如果你安装的软件是开源的，你多半还有从源码安装这个选项。

    免责声明：能用原生软件包或从源码构建，就用原生软件包或从源码构建。应用商店里那种自带全部依赖的应用，往往带来额外的性能与资源开销。

    小结

    只从默认仓库安装显然是最安全的，但越出默认范围往往也有充分的理由。作为系统管理员，你需要判断风险，并评估一个应用是否值得动用不同的包管理方案。

    一般原则：

    • 要接入一两个以上的额外仓库，得有充分的理由；多并不一定好。
    • 先把一个仓库的底细摸清楚，了解它潜在的缺点。

    本课命令速查（中文版新增）

    命令 用途
    sudo apt update 刷新本地软件包缓存
    apt install <包名> 从仓库安装软件包
    apt install /path/to/name.deb 安装本地 .deb 包（自动处理依赖）
    dpkg -i /path/to/name.deb 手动安装本地 .deb 包（不处理依赖）
    apt-cache dump 列出全部可用软件包
    apt-cache dump \| grep "Package:" \| wc -l 统计可用软件包数量
    apt-cache search <关键词> 按关键词搜索软件包
    apt-cache policy <包名> 查看候选版本及其来源仓库
